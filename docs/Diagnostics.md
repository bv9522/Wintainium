# Wintainium Diagnostics and Troubleshooting

Wintainium's public PowerShell operations return structured diagnostic data alongside their operation results. A presentation layer may format that data for a person, but Core does not make business decisions from console text.

## Start with the operation result

For every supported public command, keep the returned object and inspect its structured fields:

```powershell
$result = Get-WintainiumApplicationRelease -ManifestPath 'C:\Wintainium\manifests\Example.wintainium.json'

$result.IsSuccessful
$result.Status
$result.Errors | Select-Object Code, Message
$result.Warnings
$result.LogEvents
```

For validation:

```powershell
$result = Test-WintainiumApplicationDefinition -ManifestPath 'C:\Wintainium\manifests\Example.wintainium.json'

$result.IsValid
$result.Errors | Select-Object Code, Message
```

For manifest collection:

```powershell
$result = Get-WintainiumManifest -Path 'C:\Wintainium\manifests'

$result.IsSuccessful
$result.Manifests
$result.Errors | Select-Object Code, Message
```

## Update decisions without release evidence

A provider can retrieve an official page successfully but discover no versioned releases. This is common with general download or product-selection landing pages that link to installers without identifying a release version. In that case, `NoReleasesFound` means release discovery produced no usable release evidence; it does **not** mean the installed application is up to date. Core reports `DecisionIndeterminate` with reason code `NoReleaseEvidence` so callers can distinguish unknown update status from a confirmed absence of an update. Use a product-specific publisher page or another supported source that exposes versioned release evidence when available.

## Error handling

Expected operational failures are represented in the `Errors` collection. Error records provide a stable machine-readable `Code` and a human-readable `Message`; contextual information may also be present when the owning operation supplies it.

Use the code for automation:

```powershell
foreach ($errorRecord in @($result.Errors)) {
    switch ($errorRecord.Code) {
        'ManifestCollectionNotFound' {
            # Correct the manifest collection path.
        }
        default {
            Write-Warning "[$($errorRecord.Code)] $($errorRecord.Message)"
        }
    }
}
```

Do not write automation that matches substrings in `Message`. Diagnostic wording may become clearer without changing the machine-readable contract.

The public contract recognizes these semantic error categories:

- caller input;
- application definition;
- plugin capability;
- provider/discovery;
- acquisition;
- verification;
- installer;
- cancellation;
- internal/unexpected engine failure.

PowerShell parameter-binding and programmer errors can remain normal PowerShell errors rather than operation-result errors.

## OperationId correlation

Each public operation generates an `OperationId`. Preserve it when collecting diagnostics or handing a result to another presentation layer:

```powershell
$result.OperationId
$result.LogEvents | Format-Table
```

`OperationId` is generated by Core. Clients consume it and must not replace it with their own operation identifier.

`LogEvents` are diagnostic data. They are not a command interface and must not be interpreted as an alternate source of business rules.

## Onboarding, Installing, and Updating

All three workflows are Core-owned operations, but they do not share an identical stage plan. Onboarding already runs through the public Core command `Invoke-WintainiumApplicationOnboarding`; it intentionally does not use the eight-stage install/update orchestration lifecycle because its authoritative work is source resolution, policy resolution, normalization, and manifest persistence. The desktop onboarding service is an adapter/presenter, not the owner of those decisions. Diagnostics should share vocabulary and correlation rules without forcing onboarding into install-specific stages.

### Onboarding

The onboarding result uses `OperationId`, `IsSuccessful`, `Status`, `SourceResolution`, `ApplicationDefinition`, `ManifestPath`, `Errors`, `Warnings`, `LogEvents`, and `Stages`. The stage trace records only work reached by the operation: `InputValidation` → `SourceResolution` → `PolicyResolution` → `DefinitionNormalization` → `Persistence`. Optional icon discovery is ancillary and may add warnings, but it does not become a mandatory stage. Caller-supplied policy is represented as a successful `Skipped` policy-resolution stage. Failed stages carry a stable `ReasonCode` and human-readable `Reason` where the owning operation has evidence for them. Some failures return before later work begins, so the trace must not imply that later stages were attempted.

The authoritative success condition is `Status = Resolved` with a persisted application definition and manifest path. Source recognition alone is not successful onboarding. Onboarding does not mutate installed state.

### Installing and Updating

Install and update use the shared Core lifecycle stages, in order:

1. `ManifestValidation`
2. `ReleaseDiscovery`
3. `UpdateDecision`
4. `Download`
5. `Verification`
6. `InstallerSelection`
7. `Installation`
8. `Reconciliation`

The decision policy differs by operation: install requires an installable release for an application whose authoritative state is `NotInstalled`; update requires an available update for the currently installed application. A successful `Skipped` stage is a successful no-op, not a failed operation. Decision outcomes such as `NoInstallableRelease`, `NoUpdateAvailable`, and `DecisionIndeterminate` must remain distinguishable instead of being collapsed into a generic success or failure label.

The authoritative outcome is the completed lifecycle and reconciled installed state—not merely a successful download or installer process. Verification failure must block installation; a local hash calculated after download is not, by itself, publisher-authenticity evidence.

The default artifact-verification policy requires publisher-declared SHA-256 evidence and a matching locally computed SHA-256 digest. For first-time installation only, the desktop may offer an explicit, per-install authorization when the selected artifact has a publisher-declared MD5 checksum from the official download-page provider. After the user accepts the reduced-assurance warning, Core computes MD5 locally and requires an exact match before installation can proceed. The result is marked `VerifiedWithReducedAssurance`, with `Algorithm=MD5`, `VerificationLevel=ReducedAssurance`, and `UserAuthorized=true`. This is not equivalent to SHA-256 and does not independently establish publisher identity or file safety. An MD5 mismatch remains a hard failure; MD5 metadata from unknown sources is not eligible for consent; no checksum metadata remains a hard rejection with no override; updates do not use this install-only consent path. Diagnostics distinguish missing hash metadata (`VerificationMetadataMissing`) from metadata that exists only for unsupported algorithms (`UnsupportedVerificationAlgorithm`).

### Cross-workflow diagnostic rules

- Preserve the Core-generated `OperationId` from entry point through provider, stage, result, and desktop presentation.
- Preserve stable `ReasonCode` and human-readable `Reason` values when stage results provide them.
- Prefer the first concrete stage failure as the primary error. Generic `OrchestrationStageExecutionFailed` and `OrchestrationStageStructuredFailure` wrappers must not hide a more specific underlying failure.
- Keep the complete `Errors`, `Warnings`, `LogEvents`, stage results, and troubleshooting evidence; selecting a primary error must not discard secondary evidence.
- Treat cancellation as its own terminal outcome, distinct from failure.
- Keep workflow-specific stages distinct while aligning status semantics and error-code conventions.
- A presentation mapper must preserve meaningful successful no-op/unresolved statuses such as `Skipped`, `NoUpdateAvailable`, `NoInstallableRelease`, `DecisionIndeterminate`, `ProviderDiscoveryUnsuccessful`, and `NoReleasesFound` rather than erasing them because `IsSuccessful` is true.

The desktop's existing **Copy Diagnostics** control remains a presentation/clipboard affordance. Core diagnostic contracts and result mapping may improve, but changes to the control itself must not be used as a shortcut for correcting diagnostic data.

## Warnings and partial information

Warnings do not automatically mean that an operation failed. Check the operation's success/validity field and inspect the warning collection separately.

Likewise, a result containing useful data is not necessarily an indication that every requested action succeeded. For example, manifest collection can return successfully imported manifests while also reporting collection errors such as duplicate application IDs. The documented result contract determines how a client should interpret the operation.

## Troubleshooting by operation

### Manifest discovery

If no manifests are returned:

1. Confirm the collection path exists and is a directory.
2. Confirm files use the `*.wintainium.json` naming convention.
3. Use `-Recurse` when manifests are stored below the supplied directory.
4. Inspect `Errors` for import or collection failures.
5. Confirm duplicate application IDs are not present when collecting multiple manifests.

Manifest discovery and import are offline. A discovery problem should not be diagnosed as a provider/network problem.

### Application validation

If validation fails:

1. Inspect `Errors` by `Code`.
2. Validate the manifest against `schemas/application-manifest.schema.json`.
3. Confirm the provider and installer plugin IDs are available in the target plugin root.
4. Confirm the manifest's required plugin contract versions are compatible.
5. Confirm installer compatibility for the declared artifact policy.

A valid application definition does not establish that an update is available.

### Add Software / source resolution

When Add Software cannot resolve a URL, do not stop at the user-facing status such as
`SourceUnsupported` or `SourceResponseInvalid`. Inspect the complete onboarding result:

- `Status` — the overall terminal onboarding status.
- `SourceResolution.Status` — the selected source resolver's status when a single resolver result is available. This may be absent when multiple providers declined or when resolution failed before a provider result could be selected.
- `Errors` and `Warnings` — structured provider and Core diagnostics, including stable error codes.
- `LogEvents` — correlated provider/resolver events. Source-resolution completion events include provider identity and the provider's status in their context.
- `OperationId` — the correlation identifier to preserve when collecting or sharing diagnostics.

The Add Software flow's source-resolution diagnostics report includes the onboarding stage trace, with each reached stage's status and any available reason code/reason, alongside the provider events and structured errors. Provider trace events may include the requested and final URL paths, but query strings and fragments are removed and long paths are truncated. Raw HTML and raw request-exception text are not included in the trace.

A report with no provider/resolver events may indicate that resolution failed before a provider was invoked, no provider advertised the required capability, or the provider returned no additional events. It should not be interpreted as proof that the page itself was inspected successfully.

For a provider-resolution failure, compare the provider event's `ProviderId`, `Stage`, `Status`, and `ErrorCode` with the structured error `Code` and `Message`. A failed provider attempt emits a `ProviderSourceResolutionFailed` event with `Stage=SourceIdentification`; its `Host` field contains only the normalized hostname, never the full source URL. This preserves a per-provider explanation even when multiple providers decline and no single `SourceResolution` object can be selected. These events distinguish an unsupported host or page shape from an unavailable source, an invalid response, and an interactive/authentication requirement.

### Release discovery

If release discovery fails:

1. Check whether application validation succeeded.
2. Inspect the provider/discovery-related error code.
3. Confirm the declared provider is available and compatible.
4. If the provider requires an upstream network service, verify that the upstream source is reachable and configured as required by that provider.
5. Preserve `OperationId` and `LogEvents` when escalating or diagnosing the operation.

A successful release-discovery operation can legitimately contain no applicable release observations. Release discovery is not the update-decision stage.

For the official-download-page provider, the structured trace distinguishes retrieval from parsing:

- `ReleaseDiscoveryRequestStarted` records a redacted requested URL.
- `ReleaseDiscoveryResponseReceived` records the final URL path when available, HTTP status, content type, and HTML length.
- `ReleaseDiscoveryParsingCompleted` records the number of release-section candidates, supported download-artifact candidates, parsed artifacts, parsed releases, elapsed time, and a stable outcome.
- `ReleaseDiscoveryRetrievalFailed` and `ReleaseDiscoveryParsingFailed` identify the failure stage without copying raw HTML or exception messages that may contain signed URLs.

Interpret `NoReleasesFound` as a successful provider interaction that yielded no normalized releases—not as proof that the page was unreachable. The parsing outcome narrows the next question:

- `NoReleaseSectionCandidates`: the current parser did not recognize a release section.
- `NoSupportedDownloadLinks`: no links with currently supported artifact extensions were found.
- `ReleaseSectionsProducedNoArtifacts`: release-like sections and supported links existed, but they did not normalize into releases.
- `ReleasesParsed`: one or more releases were normalized; later eligibility diagnostics can explain why none is installable.

These counts describe what the current parser recognized; they do not claim that every possible release or download link on the page was understood. A provider may expose richer or different trace fields when its discovery method supports them.

### Update eligibility and artifact selection

The Core `ReleaseEligibilityEvaluated` event records the installed version and source, manifest channel policy, decision status/reason, and each release's normalized version and comparison outcome. It also records each considered artifact's filename, format, architecture, eligibility, and stable rejection reason. Artifact diagnostics intentionally retain only the final filename, not the full download URI, to avoid copying query strings or signed URL parameters into diagnostic reports.

Use these observations to distinguish:
- a release that is not newer or is excluded by channel/version policy;
- a newer eligible release whose artifacts are rejected by format or architecture policy; and
- an eligible release with a selectable artifact.

For example, `NoSelectableArtifact` should be investigated through the per-artifact `ReasonCode` values (such as `FormatNotPermitted`, `ArchitectureNotPermitted`, or `ArchitectureIncompatible`) rather than by loosening manifest policy without evidence.

## Installer and reconciliation diagnostics

Installer failures should be diagnosed from the structured installer error code
and lifecycle stage rather than from process text. In particular, distinguish
installer selection failures from installer execution failures:

- selection failures indicate an invalid/missing installer capability, contract
  incompatibility, unsupported artifact format, or ambiguous plugin identity;
- invocation failures indicate invalid descriptor binding, module-path/entry-point
  validation, artifact handoff, or structured settings problems;
- execution failures indicate that the selected installer process or plugin
  operation could not complete successfully.

For Windows installed-application reconciliation, an Unknown result is not a
successful NotInstalled result. Inspect the structured reconciliation evidence
and diagnostics. Multiple matching installed records are intentionally
ambiguous rather than silently resolved.

Plugin descriptor validation is an integrity boundary, not a sandbox. A valid
descriptor does not mean that the plugin's PowerShell code is untrusted or
isolated. Plugin distribution and installation are therefore trusted
administrative operations.

## JSON diagnostics

Structured results can be captured without depending on console formatting:

```powershell
$result | ConvertTo-Json -Depth 10 | Set-Content -Path 'C:\Wintainium\diagnostic-result.json'
```

When sharing diagnostics, prefer the structured result and its `OperationId` over screenshots of console output. Remove secrets or other sensitive local configuration before sharing diagnostic data.

## Logging boundary

Wintainium records structured log events within operation results so diagnostics can remain correlated with the owning operation. Logging is observational; it does not replace the operation result contract.

The public API deliberately does not promise a particular console renderer, color scheme, progress display, or diagnostic message wording. A future CLI or C#/.NET GUI can present the same structured data in its own user interface while preserving Core's business rules.

## What diagnostics cannot do

Diagnostics do not create missing application state, select an update, bypass verification, or authorize installation. In particular, clients must not attempt to reconstruct the internal update lifecycle from log events or private stage requests.

The complete public update lifecycle remains withheld until the authoritative installed-state and Core-owned composition boundaries are established.
