# Wintainium CLI Reference

## Scope

Wintainium's current public PowerShell surface is intentionally small. The engine exposes structured results that can be consumed directly by PowerShell, serialized to JSON, or presented by a future client.

The current public commands are:

- `Get-WintainiumManifest`
- `Test-WintainiumApplicationDefinition`
- `Get-WintainiumApplicationRelease`

The end-to-end application update command is **not yet public**. Update orchestration remains an internal engine capability until Wintainium has an authoritative installed-application state boundary and a Core-owned composition seam for the complete lifecycle.

## Getting started

Import the module from the repository or an installed Wintainium package:

```powershell
Import-Module .\core\Wintainium.Core\Wintainium.Core.psd1
```

Use PowerShell's built-in help for command-level guidance:

```powershell
Get-Help Get-WintainiumManifest -Full
Get-Help Test-WintainiumApplicationDefinition -Full
Get-Help Get-WintainiumApplicationRelease -Full
```

The commands return objects rather than formatted status text. This makes the same engine boundary usable from an interactive shell, automation, and a future GUI.

## 1. Discover manifests

`Get-WintainiumManifest` searches a local manifest collection and imports recognized `.wintainium.json` files.

```powershell
$result = Get-WintainiumManifest -Path 'C:\Wintainium\manifests'
```

For child directories:

```powershell
$result = Get-WintainiumManifest -Path 'C:\Wintainium\manifests' -Recurse
```

The result exposes:

- `OperationId`
- `IsSuccessful`
- `Candidates`
- `ManifestPaths`
- `Manifests`
- `Errors`
- `Warnings`
- `LogEvents`

This operation is offline and import-only. It does not discover releases, download artifacts, install applications, or manage installed state.

### Handling manifest discovery failures

Use the structured result rather than parsing terminal text:

```powershell
$result = Get-WintainiumManifest -Path 'C:\Wintainium\manifests'

if (-not $result.IsSuccessful) {
    $result.Errors | Select-Object Code, Message
}
```

## 2. Validate an application definition

`Test-WintainiumApplicationDefinition` validates one manifest and resolves the provider and installer capabilities declared by that manifest.

```powershell
$result = Test-WintainiumApplicationDefinition `
    -ManifestPath 'C:\Wintainium\manifests\example.wintainium.json'
```

The result exposes:

- `OperationId`
- `IsValid`
- `Manifest`
- `ProviderPlugin`
- `InstallerPlugin`
- `Errors`
- `Warnings`
- `LogEvents`

Validation does not perform network discovery, download, installation, or installed-state management.

## 3. Discover releases

`Get-WintainiumApplicationRelease` validates an application definition, resolves its provider, and discovers normalized release observations through the provider boundary.

```powershell
$result = Get-WintainiumApplicationRelease `
    -ManifestPath 'C:\Wintainium\manifests\example.wintainium.json'
```

The result exposes:

- `OperationId`
- `IsSuccessful`
- `Status`
- `Manifest`
- `ProviderPlugin`
- `Releases`
- `Errors`
- `Warnings`
- `LogEvents`

Release discovery does not decide whether an installed application needs an update, download an artifact, or install anything.

## Structured errors

Expected operation failures are returned in `Errors` as structured objects. At minimum, an error provides:

- `Code` — machine-readable identifier;
- `Message` — human-readable explanation.

Client code should branch on `Code` (and documented status properties) rather than parsing `Message` text.

The public error vocabulary distinguishes caller input, application-definition, plugin-capability, provider/discovery, acquisition, verification, installer, cancellation, and internal failures. Individual operations own their exact codes.

## JSON and automation

Because public results are structured objects, they can be serialized without scraping console output:

```powershell
$result = Get-WintainiumManifest -Path 'C:\Wintainium\manifests'
$result | ConvertTo-Json -Depth 10
```

Normal PowerShell object operations such as `Select-Object`, `Where-Object`, and `ForEach-Object` can be used directly against the result.

## Operation correlation

`OperationId` is generated by Core. Clients must not generate, replace, or reinterpret it as their own operation identifier.

When an operation delegates work internally, the parent operation identifier remains the correlation key for the public operation.

## What is not public yet

Wintainium does not currently expose a public command that performs the complete:

`ManifestValidation → ReleaseDiscovery → UpdateDecision → Download → Verification → InstallerSelection → Installation`

lifecycle.

This is intentional. The locked orchestration lifecycle requires internal stage composition, while the locked update-decision contract also requires authoritative installed-application state. Exposing a wrapper before those dependencies are real would force callers to construct private engine objects or would require fabricated state.

The eventual public update command will hide those implementation details behind the same structured public boundary used by the current commands.
